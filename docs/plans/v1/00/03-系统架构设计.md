## 3.2 Provider 抽象层

核心设计模式：**策略模式（Strategy Pattern）**，不同的云 GPU 厂商/接入方式实现同一套 Provider 接口。

### Provider 接口

```python
class CloudProvider(ABC):
    """云 GPU 提供商的抽象接口"""
    
    @abstractmethod
    def upload_file(self, local_path: str, remote_path: str) -> bool:
        """上传文件到云 GPU"""
    
    @abstractmethod
    def download_file(self, remote_path: str, local_path: str) -> bool:
        """从云 GPU 下载文件"""
    
    @abstractmethod
    def run_command(self, command: str, **kwargs) -> dict:
        """在云 GPU 上执行命令"""
    
    @abstractmethod
    def check_gpu(self) -> dict:
        """检查 GPU 状态（数量、显存、型号）"""
    
    @abstractmethod
    def file_exists(self, remote_path: str) -> bool:
        """检查远程文件是否存在"""
```

### 内置实现

| Provider | 传输方式 | 适用场景 | 示例厂商 |
|----------|---------|---------|---------|
| `SSHProvider` | SSH + SFTP | 有 SSH 访问权限的云服务器 | AutoDL, Vast.ai, 阿里云, 腾讯云 |
| `HTTPProvider` | HTTP multipart / REST API | 部署了推理 API 的后端 | Modal, Replicate, 自建API |
| `AutoDLProvider` | AutoDL 官方 API | 使用 AutoDL 特定功能（可扩写） | AutoDL |

### 运行时切换

```python
# 配置驱动：在 config 中指定 provider_type
config:
  provider:
    type: "ssh"  # 或 "http"
    # SSH 模式参数
    host: "xxx"
    port: 22
    username: "root"
    key_filename: "~/.ssh/id_rsa"
    
    # HTTP 模式参数（type 为 http 时）
    # api_base_url: "https://api.example.com"
    # api_key: "..."
```

## 3.3 TTS 模块的可部署位置

TTS 模块（CosyVoice）可以灵活选择部署位置：

| 部署位置 | 硬件要求 | 优点 | 缺点 |
|---------|---------|------|------|
| **本地 Mac** 🏠 | CPU 即可，M4 Pro 64GB 绰绰有余 | 免费、无网络依赖、低延迟 | 占用本地资源 |
| **云 GPU 服务器** ☁️ | GPU 可选（也可 CPU 跑） | 集中管理、利用云端 CPU 资源 | 增加上传数据量 |
| **独立 TTS 服务** 🚀 | CPU/GPU 均可 | 微服务化、可独立扩缩 | 架构复杂度增加 |

**设计原则**：TTS 位置**可配置**，通过配置项 `tts.run_on` 控制：

```yaml
tts:
  engine: "cosyvoice"
  run_on: "local"       # 可选: "local" | "cloud" | "remote_service"
  model_dir: "pretrained_models/CosyVoice-300M-SFT"
  default_speed: 1.0
```

当 `run_on: "cloud"` 时，Pipeline 会自动将文案文本发送到云 GPU，在云端执行 TTS 后直接用于推理，减少一次音频文件传输。

## 3.4 文件传输的通用设计

### 传输方式矩阵

| 传输方式 | Provider | 适用场景 | 大文件性能 |
|---------|---------|---------|-----------|
| **SFTP** | SSHProvider | 直接服务器管理 | 中等，受 SSH 加密影响 |
| **HTTP Upload/Download** | HTTPProvider | API 化部署 | 快，支持断点续传 |
| **对象存储中转** | 两种 Provider 均可 | 超大规模生产 | 极快，需额外配置 OSS/S3 |

### 传输策略

```python
class TransferStrategy(ABC):
    """文件传输策略抽象"""
    
    @abstractmethod
    def upload(self, src: str, dst: str, **kwargs) -> bool: ...
    
    @abstractmethod
    def download(self, src: str, dst: str, **kwargs) -> bool: ...
    
    @abstractmethod
    def list_files(self, path: str) -> list[str]: ...

# 实现
class SFTPTransfer(TransferStrategy):
    """基于 SFTP 的文件传输"""
    
class HTTPTransfer(TransferStrategy):
    """基于 HTTP multipart 的文件传输"""
```

## 3.6 部署架构灵活组合

| 场景 | TTS 位置 | 推理位置 | 传输方式 | 典型用户 |
|------|---------|---------|---------|---------|
| **开发调试** | 本地 | SSH 云 GPU | SFTP | 个人开发者 |
| **生产流水线** | 本地 | SSH 云 GPU | SFTP | 小团队 |
| **Serverless** | 云端 | HTTP API | HTTP | 企业用户 |
| **全云化** | 云端（同一台） | 同台云 GPU | 本地文件 | 高性能需求 |
| **混合云** | 本地 | 多家云 GPU | SFTP/HTTP | 大流量场景 |

## 3.7 关键技术决策

### Provider 不是插件化，而是配置化

**不**做成动态加载插件，而是：
1. 内置 SSH、HTTP 两种 Provider
2. 通过 `provider.type` 配置切换
3. Provider 接口保持稳定，方便扩展

### 文件传输不做自动路由

- 用户通过配置明确选择 Provider 和传输方式
- 不添加自动故障转移的复杂度
- 保持架构简单、可预测

### TTS 位置灵活但默认本地

- 80% 场景 TTS 在本地 CPU 运行就够用
- 云端部署 TTS 作为可选项，通过配置切换
- 不对齐到具体的云端路径，由 Provider 抽象处理
